## Summary

An on-chain registry of deployed LEZ programs, written with the SPEL framework, with entry IDLs and reproducible source archives on Logos Storage. Deployer entries must be signed by the program's own header account and live at a deterministic PDA, so any client can tell them apart from third-party entries from chain state alone. Authors alone can update their entries; third-party authorship moves only with both signatures. Discovery (lookup by program ID, enumeration, search by name, author, and kind) reads accounts directly from the sequencer with no indexer. A CLI rebuilds recorded sources in RISC Zero's Docker builder, compares the ImageID with the deployed program header, and stores a per-user "locally verified" mark. A Rust SDK and a Logos Core Module built with `mkLogosModule` expose registration, resolution to metadata and IDL (degrading to "IDL unavailable"), and search.

## Approach

**Program address and deployer identity.** Since LEZ `v0.2.5` a program lives at its program-loader header account, whose key the deployer holds; the ImageID is a property of the header, not the address. The registry therefore requires the header account itself to sign a deployer registration, checks that it is owned by the program loader and decodes as a `ProgramHeader`, and stores the entry at `PDA("deployer_entry", program_id)`. Alternatives considered: trusting a caller-supplied "deployer" field (forgeable), or matching the fee payer of the deploy transaction (not visible to a program at execution time and not a stable identity). The header key is the only identity the chain itself ties to the program.

**Discovery without an indexer.** Every account is a PDA: one state account with a counter, one slot account per index pointing at an entry, and entry accounts keyed by program (and author for third parties). Lookup is a single PDA read; enumeration walks the slots; search filters the enumeration client-side. An off-chain index would be faster for very large registries but reintroduces the trusted service the prize excludes; it can be layered on later as an optional cache.

**Metadata only on-chain.** Strings are length-limited (a maximal entry is about 1.6 KB). IDLs and source archives are Logos Storage CIDs. The entry copies the header's ImageID and immutability flag (33 bytes) so a client sees whether the program was redeployed since the entry was last updated.

**Verified source hosting.** The CLI uploads `git archive <commit>` to Logos Storage and records the CID as the code pointer; verification fetches from Logos Storage, not from a forge, so a deleted GitHub repository does not break re-verification. A forge URL is optional and informational only.

**Trusted-signer overlay.** Deliberately not shipped: labels come only from chain-derivable facts and from the user's own local marks, which live in a plain JSON file the user can inspect and edit.

**Things that did not work.** The `spel` CLI encodes `u64` PDA seed arguments differently from the guest macros (big-endian right-aligned vs little-endian), so slot PDAs seeded by `arg("index")` failed for every index above 0 against a real sequencer. Slots are now seeded with a `[u8; 32]` key that the program checks against the index. Passing a wallet-held account as the "program" of a deployer entry is the path that reaches the chain and is rejected there; trying to register for someone else's program fails earlier, because the wallet cannot sign for a header key it does not hold.

**Why the Logos stack.** A registry is useful only if nobody can quietly rewrite who deployed what or censor entries. On LEZ the deployer claim is enforced by the program and the signature of the program's own header key, entries are timestamped by the chain clock, and every client verifies the same state; Logos Storage keeps IDLs and source content-addressed, so pointers cannot be swapped silently. A centralised registry (as with many explorers' verified-source lists) can be edited, taken down, or made to favour particular verifiers.

## FURPS Self-Assessment

### Functionality

Register (deployer or third party), update, transfer authorship, lookup, enumerate, search, publish IDLs and sources to Logos Storage, rebuild and verify sources, and keep local verification marks. Limitations: search is a client-side scan; only RISC Zero Docker builds are supported as a reproducible build configuration; not yet deployed on testnet 0.4.

### Usability

One CLI with environment-variable defaults; signing is delegated to the user's existing LEZ wallet through `spel`, so no new key management. The SDK has a worked example for the main integration path (program ID to metadata and IDL), and the Core Module returns JSON for UI modules. `scripts/e2e-standalone.sh` runs the whole flow from a clean checkout.

### Reliability

All authorisation is enforced on-chain; clients re-check results after each transaction because SPEL reports confirmation even for rejected instructions. Missing or invalid IDLs degrade to "IDL unavailable" without failing a view. Field limits keep every instruction far below the cycle budget. Storage downloads are size-capped.

### Performance

Register costs about 60k user cycles with typical fields and about 75k at maximum field sizes; update about 41k to 77k. All are under 0.3M total cycles against a 32M public budget. Lookup is one or a few RPC reads; search over `n` entries is `2n + 1` reads.

### Supportability

Unit tests for the program logic, SDK, and FFI; IDL drift check; E2E test against a real standalone sequencer and Logos Storage node; Core Module Nix build; all in CI. The layered structure (core types, pure logic, guest, SDK, CLI, FFI, module) follows `lez-programs` conventions. Versions are pinned (SPEL `c6f73ce`, LEZ `v0.2.5-rc2`, RISC Zero 3.0.5, Logos Storage `v0.5.3`).
